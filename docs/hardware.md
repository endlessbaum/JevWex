# ハードウェア設定

拡張を再読み込みしてタブを開き直すと、左メニューに「ハードウェア設定」が表示されます。

1. 「処理方法」でCPUまたはGPU（WebGPU）を選択します。GPUを取得できない環境ではGPUの選択を無効にし、理由を表示します。
2. CPUスレッド数を選択します。自動は論理コア数の半分（切り捨て、最低1、最大8）です。手動は検出コア数まで、最大32です。複数スレッド非対応環境では自動も1スレッドになります。
3. GPUでは、すべての層または一部の層を選べます。GPUメモリ不足のときは層数を減らすかCPUに戻してください。
4. 文章量は1,024／2,048／4,096／8,192トークンです。判定基準と出力も含めた上限で、文字数ではありません。大きくするほど速いという設定ではありません。
5. 「設定を保存」は次のモデル読込へ適用します。既に読み込み済みなら「モデルを再読み込みして適用」を押してください。判定中は適用ボタンを無効にします。

初期設定はCPU・スレッド数自動・文章量4,096です。ハードウェア設定と最後に使用したモデルの識別情報を拡張オリジンのlocalStorageへ保存します。入力と結果を自動で永続保存する機能はありません。Consoleへのモデル応答出力と手動の結果保存は行えます。設定変更で推論条件が変わる場合、前回の判定結果には再実行の案内を付けます。

## 起動時のモデルと待ち時間

ハードウェア設定の「起動時のモデルと待ち時間」で変更し、同欄の保存ボタンを押します。モデルの再読み込みは不要で、起動方針は次回の管理画面起動、待ち時間は次の処理から適用します。実行中の処理の制限時間は変えません。

- 初期設定は「重いモデルを避け、軽いモデルを使う」、自動読み込みの上限は4 GiBです。前回のモデルが保存済みかつ上限以下ならそのモデルを使います。ファイル容量による起動方針であり、使用メモリの予測やランタイムの上限変更ではありません。
- 前回のモデルが上限超過・サイズ不明・未保存の場合、上限以下の保存済みモデルのうち最も小さいものを使います。代替モデルの明示指定もできます。指定モデルが未保存または上限超過なら、未読込で起動します。自動ダウンロードはしません。
- 「自動では読み込まない」「サイズに関係なく前回のモデルを使う」も選択できます。自動読み込みを制限しても手動読み込みは可能です。代替モデルで起動しても、最後に手動で読み込んだモデル情報を上書きしません。画像の判定には代替モデルも画像対応である必要があります。
- モデル読込は初期180秒、判定応答は初期240秒。各1〜3,600秒まで変更できます。判定は1入力に対する基準全体が対象で、一括・リスト判定では各項目に適用します。中止ボタンは利用でき、期限到達時にも推論の中止を要求します。ランタイムの中止確認が返るまで次の推論は始めません。
- サイドパネルやショートカットにも管理画面の応答待ち時間を通知します。通信側は画像取得と中止確認のため追加150秒の猶予を持ちます。モデル読込時間と判定応答時間は別々です。

設定は `jev.runtime-settings.v1` に保存します。HTTP APIの独立エンジンにはこの管理画面の設定を転送しません。

検証：`npm test`（126件）でサイズ・代替条件・期限延長と中止を確認。`npm run test:extension:runtime-settings` ではローカルGGUF2件を公開キャッシュAPIで保存し、0.2 GiBを境にした自動切替・設定保持・代替モデルによる実推論・手動読み込みをオフラインで確認しました。大規模モデルの長時間推論はこのテストには含みません。

## 画像用ファイル（mmproj）をCPUで処理する

「画像処理（mmproj）」で「CPUを使う」を選び、「モデルを再読み込みして適用」を押します。処理方法をGPU（WebGPU）にしたまま、画像用のmmprojだけをCPUで処理できます。「設定を保存」だけの場合は次の読み込み時に反映します。設定はブラウザの再起動後や最後のモデルの自動読み込みでも使います。

初期値の「モデル本体に合わせる」は従来と同じ動作です。本体がCPUならmmprojもCPU、本体がGPUならmmprojのGPU配置を要求します。文章専用モデルにはmmprojがないため、この設定は画像対応モデルで使用します。現在のモデルの設定には「mmproj CPU」または「mmproj GPUを要求」を表示します。GPU側の表記は指定を示すもので、mmprojの実配置の確認を意味しません。

保存値は `mmprojDevice: "auto" | "cpu"`。省略した古い設定は `auto` として読み込みます。モデル本体の `n_gpu_layers` を変えず、公開wllamaの `mmproj_offload` を切り替えます。mmprojの配置先だけの変更でもモデルを再読み込みします。

検証では本体GPU＋mmproj CPU指定でLFM2.5-VL-3Bの読み込みに成功しましたが、画像1枚の判定は240秒以内に完了しませんでした。この組み合わせの推論完了は未確認です。[実行記録](mmproj-test-results.json)

## 実装

公開配布版 `@wllama/wllama@3.6.1` の `loadModel` に `n_threads`、`n_gpu_layers`、`n_ctx` を渡します。CPUは `n_gpu_layers: 0`、GPU全層は配布版と同じ99999指定です。モデルを固定せず、fork・patch・binding追加・独自WASMビルドはありません。並列スロット1・質問直列処理・入力を切り捨てない設定は維持します。

同じモデルでも設定が異なれば、旧ランタイムを解放して再ロードします。設定が同じなら不要な再ロードを省略します。GPU読込に失敗した場合にCPUへ黙って切り替える処理はありません。

CPUの実スレッド数は公開 `getNumThreads()`、文章量は公開 `getLoadedContextInfo()` から読みます。GPUへの実配置層数には公開loggerで受信した `offloaded N/M layers to GPU` の記録を使用します。指定値だけを根拠にGPU使用中と表示しません。層数を確認できない場合は「GPUを要求（使用層数は未確認）」と表示します。取得ログ全文や入力は保存せず、検出した層数だけを結果の実行情報へ含めます。

複数スレッドのSharedArrayBuffer用にmanifestへCOEP `require-corp` とCOOP `same-origin` を追加しました。CSPを緩めず、外部ホスト権限も追加しません。専用WorkerとWASMは既存のnpm配布資産を使用します。[Chromeの公式説明](https://developer.chrome.com/docs/extensions/develop/concepts/cross-origin-isolation)、[wllamaの公開ロード設定](https://github.ngxson.com/wllama/docs/interfaces/LoadModelParams.html)
